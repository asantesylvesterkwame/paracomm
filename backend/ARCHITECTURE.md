# AI Realtime Language Translator — Backend Architecture (Hono on Cloudflare Workers)

This is the strict architecture for `ai-realtime-language-translator/backend`. It is a direct translation of the proven entity based architecture in `cubbicles-backend/` (Express + Mongoose + Socket.io) to Hono + Cloudflare Workers, scaffolded from the official `cloudflare/templates/vite-react-template`. When in doubt, open `cubbicles-backend/` and mirror how it solved the same problem, then apply the Workers substitutions in section 12.

The one sentence version: **routes are thin, entities own everything about themselves under `src/files/<entity>/`, every request flows route → controller → service → repository, services return `{ success, message, data }` and never throw for expected failures, and realtime is a Durable Object per room instead of a global broadcast.**

---

## 1. Stack

| Concern | cubbicles-backend | This backend |
|---|---|---|
| Runtime | Node + Express 4 | Cloudflare Workers + Hono |
| Language | CommonJS JavaScript | TypeScript (ESM) |
| Dev server | nodemon | Vite + `@cloudflare/vite-plugin` (`bun run dev`, Workers runtime locally) |
| Database | MongoDB + Mongoose | D1 (SQLite) + Drizzle ORM |
| Cache / denylist | Redis (ioredis) | Workers KV |
| Realtime | Socket.io global `io.emit` | Durable Object per room, WebSocket Hibernation API |
| Media | multer → Cloudinary | R2, or signed direct-to-Cloudinary upload |
| Push | firebase-admin | FCM HTTP v1 via `fetch` |
| Deploy | cPanel git hook | `bun run deploy` (wrangler) |

Package manager is bun. The template's `src/react-app/` and `index.html` are vestigial for us: this Worker is API only. They stay untouched until removal is approved, and nothing in this document ever imports from them.

## 2. Directory Layout (Target)

```
backend/
  wrangler.json            Worker config: name, main, bindings, vars. The only place bindings exist.
  vite.config.ts           Vite + cloudflare() plugin
  worker-configuration.d.ts Generated Env types: bun wrangler types
  drizzle/                 SQL migrations, generated by drizzle-kit
  src/
    worker/
      index.ts             Entry: builds the Hono app, exports default + Durable Object classes
      core/
        app.ts             Hono app assembly: middleware chain, route mounting, onError, notFound
        routes.ts          Central route registry, mounts every entity under /api/v1
        response.ts        respond() success emitter + AppError → JSON mapping
        messages.ts        Global message strings
      files/               Entity modules. The heart of the backend.
        <entity>/
          <entity>.routes.ts       Hono router: middleware wiring only
          <entity>.controller.ts   HTTP adapter, no logic
          <entity>.service.ts      All business logic, returns { success, message, data }
          <entity>.repository.ts   Static class of Drizzle query builders
          <entity>.model.ts        Drizzle table schema + inferred types
          <entity>.validation.ts   zod schemas for this entity's endpoints
          <entity>.messages.ts     Entity string constants
          <entity>.utils.ts        Entity pure helpers
          __tests__/
      durable/             Durable Object classes (RoomDO), exported through index.ts
      providers/           Third party integrations behind interfaces (translation/, transcription/)
      utils/               Global helpers: auth middleware, errors, kv, pagination, notify
      constants/           PAGE_LENGTH, status codes, shared enums
```

Decision rule for placement: used by ONE entity → `src/worker/files/<entity>/`. Used by 2+ entities → `utils/`, `constants/`, or `providers/`. Start inside the entity; promote only when a second entity actually needs it.

Two deliberate divergences from cubbicles-backend, both fixes: validation schemas live inside the entity folder (not a root `validations/` dir) and are actually enforced (section 7 — in cubbicles `checkSchema` is applied but `validationResult` is never read, so validation is decorative); and there is no repository signature drift — every repository uses the generic `(query, options)` shape of `CubbicleRepository`, never the ad hoc `fetchUserByParams` style of `UserRepository`.

## 3. Entity Modules: The Five Layers

Mirrors `cubbicles-backend/files/cubbicle/` exactly, one layer per file.

### 3.1 Routes: `<entity>.routes.ts`

Middleware wiring only. Ordering convention carried over verbatim from `cubbicle.routes.js`: public paths first → auth gate → specific paths → parameterized `/:id` catch-alls last.

```ts
const roomRoutes = new Hono<AppEnv>();

roomRoutes.post("/instant", zValidator("json", createInstantRoom), createInstantRoomController);

roomRoutes.use(isAuthenticatedOrGuest);

roomRoutes.post("/", zValidator("json", createRoom), createRoomController);
roomRoutes.post("/:roomId/messages", zValidator("json", sendMessage), sendMessageController);
roomRoutes.get("/:id", getRoomByIdController);

export default roomRoutes;
```

### 3.2 Controllers: `<entity>.controller.ts`

The HTTP adapter. Same six line shape as every cubbicles controller: gather input, call the service with the actor last, map the result. `manageAsyncOps` is not ported — Hono's `app.onError` catches unexpected throws globally (section 6).

```ts
export const createRoomController = async (c: Context<AppEnv>) => {
  const body = c.req.valid("json");
  const data = await RoomService.createRoom(c.env, body, c.get("actor"));
  if (!data.success) throw new AppError(data.message, StatusCodes.BAD_REQUEST);
  return respond(c, StatusCodes.SUCCESS, data);
};
```

Controllers pass exactly three kinds of things to services: validated input (`c.req.valid(...)`), `c.env` (bindings), and `c.get("actor")` (the decoded token, the Workers equivalent of `res.locals.jwt`). Nothing else. Controllers never touch the database, never emit socket events, never build responses beyond `respond`.

### 3.3 Services: `<entity>.service.ts`

`class RoomService { static async ... }`, no instances, all business logic. The cubbicles result contract is law: **services never throw for expected failures** — they return a discriminated result the controller maps.

```ts
static async sendMessage(env: Env, body: ISendMessage, actor: IActor) {
  const room = await RoomRepository.fetchOne(env, { id: body.roomId });
  if (!room) return { success: false, message: roomMessages.ROOM_NOT_FOUND };
  if (!isMember(room, actor)) return { success: false, message: roomMessages.NOT_A_MEMBER };

  const message = await MessageRepository.create(env, buildMessage(body, actor));
  await RoomEvents.emit(env, room.id, "message:new", message);
  return { success: true, message: roomMessages.MESSAGE_SENT, data: message };
}
```

Success shape: `{ success: true, message, data, count? }` (`count` on list endpoints only, `data` omitted on pure mutations). Failure shape: `{ success: false, message }`. Realtime emission happens inline from services through the single `RoomEvents` choke point (section 9), exactly as cubbicles services call `SocketClient.send` — but never from controllers.

### 3.4 Repositories: `<entity>.repository.ts`

Static class wrapping Drizzle. The only layer that imports the schema or query builder. Soft delete is injected here (`isDeleted = false` on every fetch), not in services — same as `CubbicleRepository.fetch` forcing `isDelete: false`.

```ts
class RoomRepository {
  static async fetch(env: Env, where: SQL, options: IFetchOptions = {}) {
    const { limit = PAGE_LENGTH, cursor, orderBy } = options;
    ...
  }
  static async fetchOne(env: Env, query: Partial<IRoom>) { ... }
  static async create(env: Env, payload: INewRoom) { ... }
  static async update(env: Env, query: Partial<IRoom>, changes: Partial<IRoom>) { ... }
  static async softDelete(env: Env, query: Partial<IRoom>) { ... }
}
```

Every repository exposes the same verbs: `fetch`, `fetchOne`, `create`, `update`, `softDelete`. Pagination is **cursor based** (`createdAt` + id cursor), not offset — cubbicles' offset `queryConstructor` with its 100 row default is the pattern we are retiring, because messages are the hot path here.

### 3.5 Models: `<entity>.model.ts`

Drizzle table definitions plus inferred types. Messages are a **first class table**, never embedded in the room row — cubbicles' embedded `Cubbicle.messages[]` array is its single worst modelling decision (whole history fetched and broadcast on every send, 16MB document cap) and does not get ported.

```ts
export const messages = sqliteTable("messages", {
  id: text("id").primaryKey(),
  roomId: text("room_id").notNull().references(() => rooms.id),
  senderId: text("sender_id").notNull(),
  senderType: text("sender_type", { enum: ["user", "guest"] }).notNull(),
  content: text("content"),
  sourceLang: text("source_lang"),
  translations: text("translations", { mode: "json" }).$type<ITranslations>(),
  createdAt: integer("created_at", { mode: "timestamp_ms" }).notNull(),
  isDeleted: integer("is_deleted", { mode: "boolean" }).notNull().default(false),
}, (t) => [index("messages_room_created").on(t.roomId, t.createdAt)]);

export type IMessage = typeof messages.$inferSelect;
```

Schema changes ship as drizzle-kit migrations in `drizzle/`, applied with `wrangler d1 migrations apply`.

## 4. Route Registration: `core/routes.ts`

Single central registry, no auto discovery — the direct translation of `cubbicles-backend/core/routes.js`:

```ts
export const registerRoutes = (app: Hono<AppEnv>) => {
  const base = "/api/v1";
  app.route(`${base}/rooms`, roomRoutes);
  app.route(`${base}/messages`, messageRoutes);
  app.route(`${base}/guests`, guestRoutes);
  app.route(`${base}/users`, userRoutes);
  app.route(`${base}/config`, configRoutes);
};
```

Conventions carried over: plural nouns, `/api/v1` prefix, actions as POST sub-paths (`/:roomId/messages`, `/:id/translations`, `/rooms/instant`), specific before parameterized.

## 5. App Assembly: `core/app.ts` and `src/worker/index.ts`

`core/app.ts` mirrors `cubbicles-backend/core/app.js` middleware ordering: parsers are built into Hono, then `secureHeaders()` (helmet equivalent), `cors()` with origins from env vars, the `emailCheck` normalizer as Hono middleware, a `GET /` health check, `registerRoutes(app)`, then `app.notFound` and `app.onError`.

`src/worker/index.ts` stays tiny, like cubbicles' 3 line `index.js`:

```ts
const app = buildApp();
export { RoomDO } from "./durable/RoomDO";
export default app;
```

## 6. Errors and the Response Envelope

cubbicles has four competing response shapes (success, business failure wrapped in `errors`, auth, validation) and returns 400 for both unknown routes and unexpected crashes. We unify to **one envelope, correct status codes**:

- Success: `respond(c, status, result)` → HTTP 200/201, body `{ success: true, message, data, count? }` — the service result verbatim, same as cubbicles' `responseHandler`.
- Expected failure: controller throws `AppError(message, status)`; `app.onError` maps it to `{ success: false, message }` with its status (400 business, 401 auth, 403 forbidden, 404 missing resource).
- Validation failure: the zod hook returns 422 `{ success: false, message, errors }` where `errors` is the flattened field error list.
- Unknown route: `app.notFound` → **404** `{ success: false, message }` (cubbicles returns 400 — bug, not ported).
- Unexpected throw: `app.onError` fallback → **500** `{ success: false, message: generalMessages.UNEXPECTED_FAILURE }`, real error to `console.error` (visible in `wrangler tail` / observability).

`AppError` lives in `utils/errors.ts` and is the only error class. `manageAsyncOps` and `CustomError`'s habit of stuffing the whole service result into `errors` are not ported.

## 7. Validation: zod, Colocated, Enforced

express-validator `checkSchema` translates to zod + `@hono/zod-validator`. Schemas live in `files/<entity>/<entity>.validation.ts`, applied in the routes file, consumed in controllers via `c.req.valid(...)` so services only ever see typed, validated input.

```ts
export const sendMessage = z.object({
  content: z.string().trim().min(1).max(5000),
  sourceLang: z.string().regex(BCP47_REGEX).optional(),
  replyTo: z.string().ulid().optional(),
});
```

Every mutating endpoint gets a schema. No decorative validation, no ad hoc `if (!content?.trim())` guards duplicated inside services for things the schema already proves.

## 8. Auth: Clerk

Auth is delegated to Clerk: this backend never issues login tokens — it verifies Clerk session JWTs. `utils/auth.ts` provides:

- `isAuthenticated` — rejects with a clean 401 `AUTH_NOT_CONFIGURED` when `CLERK_SECRET_KEY` is absent, otherwise composes `clerkMiddleware()` from `@hono/clerk-auth`, reads `getAuth(c)`, and sets `c.set("actor", { type: "user", clerkId })`. 401 `UNAUTHENTICATED` when no session.
- `verifyWsToken(env, token)` — `verifyToken` from `@clerk/backend` for the WebSocket upgrade path, where the token arrives as a query parameter instead of an `Authorization` header. Returns the clerkId or null; all verification happens in the Worker before any Durable Object sees the request.

The identity indirection is preserved: the Clerk user id is not a local row id. Every service resolves the local user through `UserUtils.requireCurrentUser(env, actor)` against a `users.clerkId` unique column. The row is created lazily by `UserService.getMe` on first authenticated request — the only place the Clerk Backend API (`clerkClient.users.getUser`) is called; user search always hits D1.

Controllers may pass `c.executionCtx` to services that do fire-and-forget work (`ctx.waitUntil`), one extra argument over the standard trio.

Guest sessions are future work — not implemented. Chat is auth-only and `/live` needs no token at all (IP quota).

Secrets: `CLERK_SECRET_KEY` via `.dev.vars` locally and `wrangler secret put` in prod; `CLERK_PUBLISHABLE_KEY` is non-secret and lives in `wrangler.json` vars.

## 9. Realtime: Durable Object per Room

Socket.io does not run on Workers, and cubbicles' socket layer is the part the platform plan already condemned: a global unauthenticated `io.emit` to every connected client, event names abused as room identifiers, an arbitrary event relay in `typing`, a double emit bug in `SocketClient.send` (`utils/socket.js:37-41`), and an O(members) full list re-query and broadcast per message. **None of that is ported.**

The replacement:

- `durable/RoomDO.ts` — one Durable Object instance per room (`idFromName(roomId)`), using the WebSocket Hibernation API. Clients connect to `GET /api/v1/rooms/:roomId/ws?token=...`; the Worker validates the JWT (user or guest, membership checked) before upgrading and forwarding to the DO.
- Event names keep the cubbicles `entity:action` grammar but drop the id-in-the-name hack, since delivery is already scoped to the room's sockets: `message:new`, `message:updated`, `message:deleted`, `message:seen`, `message:reaction`, `room:updated`, `typing:start`, `typing:stop`. Payloads are the single affected entity, never the whole room with full history.
- `typing` is a validated, fixed-shape event relayed only to the sender's room — the arbitrary `data.eventName` relay is banned.
- All emission goes through one choke point, `utils/roomEvents.ts` (`RoomEvents.emit(env, roomId, event, payload)`), which resolves the DO stub and calls its broadcast method — the same single-seam role `SocketClient.send` plays in cubbicles services, minus the double emit.
- Room member list updates (the `cubbicle:user:all:<userId>` fan-out) are replaced by a slim `room:updated` event carrying only the changed room summary. No per-member full list re-queries, ever.

## 10. Providers: Pluggable Integrations

`src/worker/providers/` mirrors `cubbicles-backend/providers/` but every provider sits behind an interface with an ordered fallback registry, per the translator plan:

```
providers/translation/
  translation.provider.ts     translate(text, from, to), detect(text), name, charBudget
  deepl.provider.ts
  gemini.provider.ts
  translation.registry.ts     ordered chain, skips providers over their KV monthly char budget
```

The consuming seam is the service layer, at the same place cubbicles hooks `filterContent` into `sendMessage` (`cubbicle.service.js:705`): the message persists and emits immediately with original text, then translation runs fire and forget via `c.executionCtx.waitUntil(...)` (the Workers replacement for `setImmediate`) and emits `message:updated` when done. Chat latency never waits on a provider. Translation results cache in the message row's `translations` map first, then KV by text hash.

## 11. Config and Bindings

There is no dotenv and no `core/config.js`. The translation:

- Non-secret config → `vars` in `wrangler.json` (and `.dev.vars` locally). Secrets (`JWT_ACCESS_SECRET`, `GUEST_JWT_SECRET`, `DEEPL_API_KEY`, `GEMINI_API_KEY`) → `wrangler secret put`, never committed. cubbicles commits its `.env` and a Firebase service account JSON to the repo — that practice stops here.
- Bindings (`DB` for D1, `DENYLIST`/`CACHE` for KV, `ROOM_DO`, `MEDIA` for R2) are declared in `wrangler.json` and typed by running `bun wrangler types` after any change, which regenerates `worker-configuration.d.ts`.
- Code accesses env exclusively through the typed `Env` on `c.env` — `process.env` does not exist. No dead keys: every var in `wrangler.json` is referenced, every referenced var is declared.
- Feature flags: port `files/config/` as is — a D1 backed key/value entity with public `GET /api/v1/config/feature-flags` flattening rows into `{ [key]: value }`. It is the smallest cubbicles entity and the template for scaffolding new ones. Flags to launch with, from the plan: `ENABLE_TRANSLATION`, `ENABLE_TRANSCRIPTION`.
- Scheduled work uses Cron Triggers in `wrangler.json` (e.g. expired instant room sweep). cubbicles' self-ping keep-alive cron has no Workers equivalent and is not ported.

## 12. Substitution Table (When Mirroring cubbicles-backend)

| cubbicles-backend | Here |
|---|---|
| `res.locals.jwt` / `req.payload` | `c.get("actor")` |
| `manageAsyncOps` tuple + `next(error)` | throw `AppError`, caught by `app.onError` |
| `responseHandler(res, status, data)` | `respond(c, status, data)` |
| `SocketClient.send("cubbicle:<id>:event", data)` | `RoomEvents.emit(env, roomId, "event", data)` |
| `RedisClient.get/setCache` | KV namespace on `c.env` |
| Mongoose model + `CubbicleRepository` | Drizzle table + same-verbs repository |
| `uploadManager(...)` multer → Cloudinary | R2 binding or signed direct upload |
| `queryConstructor` offset pagination | cursor pagination in the repository |
| `setImmediate` fire and forget | `executionCtx.waitUntil(...)` |
| `checkSchema` (unenforced) | `zValidator` (enforced) |
| `node-cron` | Cron Triggers |

Known cubbicles defects that must not survive the port: the socket double emit, the unauthenticated socket layer, the embedded messages array, the per-member list fan-out, decorative validation, 400 for not-found, the four inconsistent response shapes, the `notification.service.js` undefined `user` reference on high urgency bulk sends, and the module-load side effect DB connect in `notification.utils.js`.

## 13. Checklist: Adding a New Entity

1. Scaffold `src/worker/files/<entity>/` with the files from section 2. Copy the `config` entity as the starting shape.
2. Define the Drizzle table in `<entity>.model.ts`, generate and apply a migration.
3. Repository with the standard verbs, soft delete and cursor pagination included.
4. Service statics returning `{ success, message, data }`, realtime through `RoomEvents` only.
5. zod schemas in `<entity>.validation.ts`, applied in the routes file.
6. Six line controllers.
7. Routes file with the ordering convention, mounted in `core/routes.ts`.
8. Vitest tests beside the entity in `__tests__/`, mocking the repository and `RoomEvents` seams like `cubbicle.test.js` does.
9. New binding or secret → declare in `wrangler.json`, run `bun wrangler types`.

## 14. Hard Rules

- No logic in routes files; no HTTP in services; no database access outside repositories; no Drizzle imports outside `<entity>.model.ts` and `<entity>.repository.ts`.
- Services never throw for expected failures and never return anything but the `{ success, message, data, count? }` contract.
- All realtime emission through `RoomEvents`; no direct DO stub calls from services.
- Every mutating endpoint has an enforced zod schema.
- No `process.env`, no committed secrets, no untyped `c.env` access.
- Messages and other unbounded lists are rows, never embedded arrays; list endpoints are cursor paginated.
- One response envelope, correct status codes, 404 means not found.
- No new top level folders without updating this document.
